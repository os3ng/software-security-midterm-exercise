Chapter 1 — Overview of Software Security

1. What is software security?

Engineering software so it continues to function correctly even under malicious attack. Security should be addressed early, not bolted on only after development.

Easy idea: Quality asks “works correctly?” Security asks “still works safely when attacked?”
2. CIA Triad
CConfidentiality — prevent unauthorized disclosure.
IIntegrity — prevent unauthorized alteration.
AAvailability — information/service is available when required.
3. Defect, Bug, Flaw, Failure, Risk, Vulnerability
TermEasy meaningExample
DefectDeviates from requirement/specificationRequirement says password ≥8 chars; app accepts 5.
BugCoding/implementation errorLogin button crashes app.
FlawDesign/architecture/logic weaknessPasswords stored in plaintext.
FailureSoftware cannot perform required functionService fails to process login.
RiskProbability × impact of a problemChance and consequence of account compromise.
VulnerabilityExploitable weakness/errorDynamic SQL vulnerable to injection.
4. Three pillars of software security

Risk Management — identify, rank, track, understand and handle risks.
Touchpoints — concrete security activities applied during development.
Knowledge — gather/share principles, guidelines, vulnerabilities, exploits, attack patterns and historical risks.

Mnemonic: RTK = Risk, Touchpoints, Knowledge.
5. Risk Management Framework (RMF) — 5 activities
  1. Understand business context — goals, critical assets/operations, scope.
  2. Identify business & technical risks — threats, vulnerabilities, likelihood, business impact.
  3. Synthesize, prioritize & rank — likelihood, impact, priority.
  4. Define mitigation strategy — cost, time, success likelihood, competence, impact; decide validation.
  5. Carry out fixes & validate — implement mitigation and confirm unacceptable risk is removed/reduced.
Remember: Context → Identify → Rank → Mitigate → Validate. Risk management is continuous, not once only.
6. Seven software security touchpoints
  1. Abuse Cases — think about abnormal/malicious behavior; create anti-requirements and attack models.
  2. Security Requirements — explicitly define security goals and assumptions.
  3. Architectural Risk Analysis — find design flaws using attack resistance, ambiguity and weakness analysis.
  4. Risk-Based Security Testing — inside-out, attacker mindset, starts before system is complete.
  5. Code Review — source-code/static analysis to find security bugs.
  6. Software Penetration Testing — outside-in simulated attack on the final system.
  7. Security Operations — learn from real attacks and feed knowledge back into development.
7. Architectural Risk Analysis — 3 aspects

Attack Resistance: known attacks/checklists and whether attacks are viable.
Ambiguity Analysis: creative search for new risks; benefits from multiple experienced analysts.
Weakness Analysis: risks caused by dependencies/middleware and failed assumptions.

8. Risk-based testing vs penetration testing

Risk-based security testing: inside-out, based on architecture + attacker mindset, begins before software is complete.
Penetration testing: outside-in, simulates an external attack, typically on the final system.

9. SDLC

Planning → Design → Implementation → Testing → Deployment → Maintenance.

10. Quality code vs secure code

Quality: functionality, performance, usability, maintainability.
Secure: protection against threats/vulnerabilities; supports CIA.

High quality ≠ automatically secure. Secure ≠ automatically high quality. Best software needs both.
11. Threat Modeling — purpose and process

A structured technique to identify security objectives, threats and vulnerabilities so security decisions can be prioritized.

  1. Identify security objectives — CI4AM: Confidentiality, Integrity, Availability, Authentication, Authorization, Auditing, Management.
  2. Application overview — deployment, users, data, rights, technologies, mechanisms.
  3. Decompose application — entry points, exit points, data flows, trust boundaries.
  4. Identify threats — attack trees, attacker mindset, STRIDE/DREAD, etc.
  5. Identify vulnerabilities — e.g. weak encryption, cleartext credentials, dynamic SQL, long sessions.
  6. Rank threats — probability × impact or DREAD average.

Risk responses shown in the chapter: accept, mitigate, transfer; ignoring is discouraged.

Chapter 2 — Secure SDLC (SSDLC)

1. OWASP SAMM

An open-source software security maturity framework used to assess current practices, plan improvement and measure progress.

5 business functions: Governance, Design, Implementation, Verification, Operations. Each has two practices.

FunctionPractices
GovernanceStrategy & Metrics; Policy & Compliance
DesignThreat Assessment; Security Requirements
ImplementationSecure Build; Secure Deployment
VerificationSecurity Testing; Security Review
OperationsIncident Management; Environment Management

Maturity: Level 1 Ad-hoc/basic → Level 2 Defined/repeatable → Level 3 Optimized/measured/continuous improvement.

2. Application security risk

Overall risk considers threat agent + attack vector + security weakness + likelihood + technical/business impact. Technical impact can include privacy loss/data theft/system disablement; business impact can include delayed income and increased expenses.

3. Security in every SDLC phase
PhaseSecurity activities
Planning & RequirementsRisk assessment, abuse cases, security requirements.
DesignThreat modeling; secure design principles such as least privilege and defense in depth.
ImplementationSecure coding; security-focused code reviews.
TestingStatic/dynamic analysis, penetration testing, vulnerability scanning, risk-based testing, automated tools.
DeploymentSecure configuration; strict access controls.
MaintenanceUpdates/dependency patching; incident response plan.
4. ISO/IEC 27034

Application-security framework across the software lifecycle. Key concepts:

  • ASC: specific Application Security Control, e.g. input validation.
  • ASCL: reusable library/catalog of ASCs.
  • ASLC: application security life cycle.
  • ASMP: management/governance process for application security.
  • ONF: organizational policies, standards, guidelines and reusable resources.

Important: ISO/IEC 27034 provides a framework/process; it does not itself give a ready-made control list. Other sources can provide controls.

  1. Broken Access Control
  2. Cryptographic Failures
  3. Injection
  4. Insecure Design
  5. Security Misconfiguration
  6. Vulnerable & Outdated Components
  7. Identification & Authentication Failures
  8. Software & Data Integrity Failures
  9. Security Logging & Monitoring Failures
  10. Server-Side Request Forgery (SSRF)
6. CWE

Common Weakness Enumeration = catalog of software coding/design weaknesses. Examples in the chapter include CWE-20 Improper Input Validation, CWE-74 Injection, CWE-120 Buffer Overflow, CWE-287 Improper Authentication, CWE-209 Information Exposure in Error Message, and CWE-200 Information Exposure.

7. OWASP Top 10 vs CWE

OWASP Top 10: high-level application risk categories, attacker/risk view.
CWE: detailed weakness/root-cause catalog, developer view.
One OWASP category can map to many CWEs.

8. Development methodologies

Waterfall: linear; security often late/reactive.
V-Model: testing mapped to stages; limited flexibility.
Spiral: iterative and risk-driven; security considered early.
RUP: iterative, architecture-centric; security in requirements/design.
Agile: speed/adaptability; security may be overlooked.
Secure Agile/DevSecOps: security every sprint + automated CI/CD testing.
Microsoft SDL: security throughout phases.
OWASP SAMM: assess and improve security practices.

Chapter 3 — Handling Input

1. Why input is dangerous

Input can come from users, external systems and other sources. Malicious input can become code/data that compromises the application. Therefore, classify, validate and process it securely.

2. Trusted vs untrusted input

Trusted: reliable sources such as internal systems/trusted users.
Untrusted: unknown/external sources such as web user input.

Security mindset: never assume user-controlled input is safe just because it “looks normal.”
3. Why validate input?
  1. Prevent attacks: SQL injection, XSS, command injection, malicious scripts.
  2. Protect database integrity.
  3. Ensure data accuracy.
  4. Prevent system crash.
  5. Maintain reliability.
4. Filtering, sanitization, normalization

Filtering: accept only allowed/good input.
Sanitization: clean dangerous/dirty input.
Normalization: convert input to a consistent representation.

5. Syntactical vs semantic validation

Syntactical = “Does it follow the format?” Example: email contains @, valid domain format, reasonable length, no dangerous characters.

Semantic = “Does it make sense / is it legitimate in this application?” Example: age must be within an allowed range; email ownership can be confirmed through a verification link/code.

Mnemonic: Syntax = Shape. Semantic = Sense.
6. Input prevention measures
  • Prepared statements / parameterized queries.
  • Input/output encoding where appropriate.
  • Check input size to prevent buffer overflow.
  • Access control and privilege management.
  • Hide raw database errors.
  • Use a WAF.
  • Keep software/frameworks updated.
7. SQL Injection — exam-ready explanation

SQL injection occurs when attacker-controlled input is inserted/appended into an SQL statement and the database interprets that input as SQL code.

Vulnerable idea: build SQL by concatenating user input. An attacker may add a condition such as OR 1=1, causing a condition to become true and exposing unintended records.

Best mitigation emphasized in the chapter: prepared statements / parameterized queries. The SQL structure uses a placeholder and user input is supplied separately, so the DB treats the input as data rather than executable SQL.

8. Sensitive data exposure prevention

Do not store sensitive data you do not need. Classify data. Identify what is sensitive based on legal/business needs. Encrypt sensitive data at rest using strong, current algorithms/protocols/keys. The chapter summary also emphasizes protection in transit (e.g. TLS).

  5. Carry out fixes and validate (1)

Q2. Secure SDLC Scenario (10 marks)

A team is developing an online payment application. Propose suitable security activities for the Planning/Requirements, Design, Implementation, Testing, Deployment and Maintenance phases.

Show marking guide / model points

Planning: risk assessment, abuse cases, security requirements. Design: threat modeling, least privilege/defense in depth. Implementation: secure coding + code review. Testing: static/dynamic analysis, pen testing, vulnerability scanning/risk-based testing. Deployment: secure configuration + access control. Maintenance: updates/dependency patching + incident response. Full marks require phase-appropriate explanation, not just listing tools.

Q3. Input Handling & SQL Injection (10 marks)

Explain the difference between syntactical and semantic validation. Then explain how SQL injection happens and describe suitable prevention measures.

Show marking guide / model points

Syntactical: format/syntax checks with example (2). Semantic: business meaning/context/legitimacy with example (2). SQL injection: attacker input becomes part of executable SQL, usually through unsafe concatenation (2). Prepared/parameterized query separates code and data (2). Other relevant controls: validation, least privilege/access control, hide raw DB errors, WAF, updates, appropriate encoding (2).
